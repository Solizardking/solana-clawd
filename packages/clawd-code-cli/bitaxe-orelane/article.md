## The setup

A Bitaxe Gamma `602` ASIC hashes Bitcoin at **~820 GH/s** in a closet. A
control-plane Node.js process watches it over HTTP and decides — every minute —
whether to push ORE onto a board, claim a checkpoint, or just hold. A Telegram
bot lets the operator ask "is the rig OK?" in plain English and get an honest
answer.

Until last week, that whole project lived in one folder:

```
/Users/8bit/Documents/New project 2/
├── src/             (16 .ts files: controller, policy, bot, helius, …)
├── dashboard/       (Next.js rig UI)
├── firmware/        (ESP-Miner C patch for the BM1370)
├── docs/            (architecture, ORE v3 timing, telegram-bot)
├── clawd.json       (CAAP/1.0 agent definition)
├── package.json     (3 prod deps: @solana/web3.js, bs58, chalk)
├── tsconfig.json
└── README.md        (408 lines of operator docs)
```

It worked. **46 vitest tests passed.** Telegram routes slash-commands and
natural-language prompts. The Telegram routing falls back through DeepSeek →
OpenRouter → keyword detection. The ORE policy engine respects five safety
gates (temp, CPU, heap, WiFi, pause state) before it ever fires a live deploy.
The Helius DAS client reads wallet balances. The `vulcan` CLI is wrapped for
Phoenix perp paper + live trading.

But it was *alone*. No other project could borrow its `policy` engine. No
other subpackage could trigger its Telegram bot. The `.env` file with the live
Helius key was sitting in the project root, one `git add` away from a public
push.

## The relocation

Then came the move. Goal: drop the project into
`/Users/8bit/Downloads/solana-clawd/packages/clawd-code-cli/bitaxe-orelane/`
so it could ride alongside the rest of the solana-clawd family — `clawd-grok`,
`clawd-sdk`, `agent-registry`, `agent-hub`, `pay`, `x402`, `vendor/`. Same
checkout, same git, same monorepo scripts.

Here's the recipe — copy-pasteable for any solo project that wants to join a
pnpm/npm monorepo without losing its mind.

### 1. Copy, don't move

We used `rsync` with surgical excludes. **Never** move until you've copied and
tested.

```bash
TARGET=/Users/8bit/Downloads/solana-clawd/packages/clawd-code-cli/bitaxe-orelane
mkdir -p "$TARGET"
rsync -av \
  --exclude='node_modules' \
  --exclude='.env' \
  --exclude='.DS_Store' \
  --exclude='dist' \
  --exclude='.git' \
  --exclude='.vercel' \
  --exclude='package-lock.json' \
  --exclude='.next' \
  --exclude='*.log' \
  "/Users/8bit/Documents/New project 2/" "$TARGET/"
```

Why these excludes?
- `node_modules` — regenerated by `npm install`
- `.env` — **secrets** stay in the source checkout
- `dist` — regenerated by `npm run build`
- `.git` — the new monorepo already has its own git history
- `package-lock.json` — generated fresh per install

### 2. Nuke the secret leak

The copy came in clean **except** for `dashboard/.env.local` — which had:

```
BITAXE_URL=http://192.168.1.174
RPC=https://mainnet.helius-rpc.com/?api-key=c55c146c-71ef-…
HELIUS_API_KEY=c55c146c-71ef-…
```

A live Helius API key and a home-network Bitaxe URL. That belongs in *one*
`.gitignore`-ed `.env` and nowhere else. We deleted the leak immediately and
let the user re-create it from `.env.example`.

### 3. Write the handoff docs

Two new files inside the subpackage:

- **`INTEGRATION.md`** — what this project is, how it touches the rest of the
  monorepo (pay, x402, vendor, agent registry), how to run it, what *didn't*
  move, and a link to the original GitHub for git history.
- **`CLAUDE.md`** — a 50-line quick-reference card with the 9 most important
  commands and a "see also" list. Designed to be read in 30 seconds by a
  future agent or a tired human at 3 AM.

### 4. Wire the monorepo root

The solana-clawd root `package.json` already had `clawd:build`, `clawd:dev`,
`clawd:start` that `cd` into `packages/clawd-code-cli/`. We added the same
shape for the new subpackage — 10 scripts, inserted alphabetically right
after the existing `clawd:dev`:

```json
"bitaxe:install":            "cd packages/clawd-code-cli/bitaxe-orelane && npm install",
"bitaxe:build":              "cd packages/clawd-code-cli/bitaxe-orelane && npm run build",
"bitaxe:test":               "cd packages/clawd-code-cli/bitaxe-orelane && npm test",
"bitaxe:status":             "cd packages/clawd-code-cli/bitaxe-orelane && npm run status",
"bitaxe:start":              "cd packages/clawd-code-cli/bitaxe-orelane && npm start",
"bitaxe:bot":                "cd packages/clawd-code-cli/bitaxe-orelane && npm run bot",
"bitaxe:bot:test":           "cd packages/clawd-code-cli/bitaxe-orelane && npm run bot:test",
"bitaxe:dashboard:install":  "cd packages/clawd-code-cli/bitaxe-orelane/dashboard && npm install",
"bitaxe:dashboard:dev":      "cd packages/clawd-code-cli/bitaxe-orelane/dashboard && npm run dev",
"bitaxe:dashboard:build":    "cd packages/clawd-code-cli/bitaxe-orelane/dashboard && npm run build"
```

Now from anywhere in the repo:

```bash
npm run bitaxe:status           # dry-run live snapshot
npm run bitaxe:test             # 46 vitest tests
npm run bitaxe:bot              # launch the Telegram operator
npm run bitaxe:dashboard:dev    # Next.js rig UI on :3000
```

### 5. Verify nothing broke

```bash
cd /Users/8bit/Documents/New project 2       # still has node_modules
./node_modules/.bin/tsc -p . --noEmit        # exit 0
./node_modules/.bin/vitest run               # 4 files, 46 tests, 410 ms
```

The moved code is byte-identical to the code that was compiling and passing
before the move. **Move + verify = no surprises.**

## Why this is cool

A few things make this integration feel like the right shape:

### 1. The subpackage keeps its small dep tree

`bitaxe-orelane` ships with exactly **3 prod deps** (`@solana/web3.js`, `bs58`,
`chalk`) and 5 dev deps. It does **not** get pulled into the monorepo's
`pnpm` workspace graph. It lives next to `clawd-code-cli` but doesn't pay rent
in the `@openclawdsolana/*` cluster. The whole `package.json` is 36 lines.

This is intentional. The clawd-code-cli has 18 prod deps and weighs in at
hundreds of MB with `node_modules`. The bitaxe-orelane is a **control plane**,
not a UI. Keeping it lean means it can boot on a $5 VPS in 200 ms, which is
where it actually runs (the rig closet).

### 2. The agent identity is shared

The `clawd.json` file at the root of the subpackage defines the agent with the
**CAAP/1.0** protocol — discovery URL `https://x402.wtf/.well-known/agent-auth.json`,
registration endpoint `https://x402.wtf/api/auth/agent/register`, Ed25519 keys.
This is the **same** identity protocol the rest of solana-clawd uses, so the
new subpackage is a first-class citizen of the agent registry the moment the
user publishes it. No new auth flow, no new contract, no new SDK.

### 3. The safety model is portable

`DRY_RUN=true` is the default. Live execution requires the conjunction of:
- `DRY_RUN=false`
- `LIVE_EXECUTION=true`
- `OPERATOR_CONFIRMED=true`
- Bitaxe safety gates all green (temp ≤ 72 °C, CPU ≤ 75 %, free heap ≥ 150 KB,
  WiFi RSSI ≥ -75 dBm, miner not paused)

Four keys, one operator click, five environmental checks. That entire
contract lives in `src/policy.ts` and `src/config.ts`. Nothing in the new
monorepo context changes it. The move was a **placement**, not a rewrite.

### 4. Telegram routing is multi-tier by design

```
Telegram message
   ↓
parseCommand()     — slash command? → execute directly
   ↓ no
DeepSeek routing   — deepseek-v4-pro via API
   ↓ fail or unset
OpenRouter fallback — openrouter/free
   ↓ fail or unset
Keyword routing    — 18 hand-tuned regex cases
```

Three AI tiers and a deterministic last-resort. The bot never crashes on a
network blip — `getUpdates` retries with exponential backoff. The bot refuses
to print any env var, keypair, or RPC URL. The bot is the operator surface,
and the operator's machine can be a Raspberry Pi.

### 5. The firmware overlay keeps the keypair off the device

The `firmware/esp-miner-overlay/` directory contains a C patch for
ESP-Miner that lets the Bitaxe Gamma 602 report rig state (hashrate, temp,
power, frequency) to the controller over HTTP — *without* ever storing a
Solana secret on the BM1370's flash. The whole rig runs with the keypair
locked to the VPS, not the closet. The ESP32 only sees `192.168.1.174:80`.

That separation — Bitcoin ASIC on isolated WiFi, Solana hot key on a $5 VPS
that *reads* the ASIC — is what makes the whole design safe enough to publish.

## What we did not move

Three things stayed in the original checkout:

| File | Why |
|---|---|
| `.env` | Helius key, Telegram token, DeepSeek key, ORE keypair path. One copy, one place, `.gitignore`'d |
| `node_modules/` | 4,384 entries, 600 MB. `npm install` regenerates in 8 s |
| `dist/` | 640 entries of compiled JS. `npm run build` regenerates in 2 s |
| `.git/` | The solana-clawd repo has its own git history; the original is at https://github.com/Solizardking/btcoreminingonsolana |

This is the **minimum surface area** the move touches. If something in the
new subpackage ever needs to roll back, the original folder is unchanged and
still buildable. The rsync was a copy, not a destructive move.
